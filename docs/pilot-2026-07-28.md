## Addendum — 2026-07-29 sandbox and storage hardening

The read-only signature was traced to the collaboration RPC transport rather
than the role workspace mount itself. The external role could write inside its
workspace, but the FIFO and per-call response FIFO lived under host `/tmp`.
Codex workspace-write correctly exposed that location as read-only, so every
collaboration call failed with `EROFS` and the role reported the whole
workspace as unavailable.

The transport now lives under `<role-workspace>/.opc-comms/rpc`. A supplied
workspace that cannot host the transport fails setup visibly instead of
silently falling back to `/tmp`. A real Linux bubblewrap integration test now
starts the host broker, enters the same `workspace-write` boundary used by
role tools, writes a file in the workspace, creates the response FIFO, and
completes an `inbox` RPC round trip. This closes the reproduced sandbox
boundary defect; a clean live provider-backed Company slot is still required
before changing the pilot or product-promotion verdict.

The pilot database also exposed two independent storage amplification paths:

- the 0.5-second dispatcher poll persisted and emitted
  `member_inbox_updated` for every role even when no state changed
  (378,640 events / about 318 MB in the preserved pilot DB);
- Native Runtime streaming deltas were stored in both `runtime_events` and
  generic `events`, while suspend checkpoints copied complete WorkItem
  metadata twice.

Inbox state now uses a stable fingerprint and writes only on change. Streaming
fragments remain available live but are not durable recovery records, generic
runtime-event duplication is suppressed, in-memory event history is bounded,
verification evidence is stored as a bounded preview with original length and
SHA-256 identity, and suspend checkpoint schema v3 retains execution identity
without embedding unbounded WorkItem outputs.
