## Harness defects found and fixed during the pilot (all committed with tests)

1. `opc exec --json` output was hard-wrapped by the rich console at terminal
   width, corrupting every substantial payload (`5b8bb9e`).
2. `opc exec` reported `ok: true` / exit 0 for failed and cancelled tasks;
   it now probes terminal task status and exits 3 on failure (`caf321f`).
3. First-use tool approval blocked headless task slots (runtime config:
   `tool_first_use_approval: false`).
4. Company staffing preflight is a two-checkpoint chain answered via
   ordinary `session send` messages (`672c62a`, `6e4b34e`).
5. `--force` reruns collided with the durable terminal-state guard; forced
   reruns now reopen the manifest with an audit trail (`9393566`).
6. Undersized slot timeouts killed genuinely progressing company runs.
7. Dispatch acknowledgements were accepted as deliverables; they are now
   recognized and nudged with `continue` until real delivery (`3ee545e`).

The harness's fail-closed verdict (empty output, blocked text, malformed
JSON = failure) surfaced every one of these instead of laundering junk data
into "completed" slots.

## Verdict and consequences

- The Task-vs-Company product claim remains **unanswerable** until the
  claim livelock is root-caused and fixed; timeouts and scope reduction do
  not help a non-converging run.
- This strengthens the 2026-07-21 adoption verdict with quantified,
  reproducible evidence: company-mode headless reliability is the gating
  defect, now with a precise signature to debug against.
- Measured pilot spend stayed within the $20 ceiling; canary evidence
  collection (5-minute status cron) and ARK key renewal are now automated
  independently of any resident process.

## Recommended next steps

2. Re-run one company slot as regression proof after the fix, then decide
   pilot scale (reduced 4-pair round first).
3. Human confirmation of the 3 pending task-arm judgment drafts

## Addendum — 2026-07-29 overnight livelock resolution

Six forced reruns of `software-race-fix/company/2` (durable state carries
across attempts) produced, in order:

1. **Livelock variant 1 fixed and verified live** (`ff05889`): stale shared
   work-item objects re-enqueued non-dispatchable cards every tick. After
   the fix: zero claim losses in the 07-29 logs.
2. **Livelock variant 2 fixed and verified live** (`46d0cff`): review
   verdicts projecting READY_FOR_REWORK left the settled attempt's claim
   fields, making the CAS refuse forever (4,500+ losses on one card,
   surfaced by the new WARNING escalation). After the fix the review chain
   (report v1 → review v1) completed for the first time.
3. **Headless checkpoint protocol fully mapped** (`3ee545e`, `83e8fb6`,
   `c7a9afc`): staffing selection → auto recruit, recruitment proposal →
   approve, dispatch acknowledgements and interim runtime snapshots →
   continue, parked delivery release → approve. The delivery
   *self-evolution feedback* checkpoint (`company_delivery_feedback`)
   intentionally requires an explicit checkpoint-id reply (UI review card)
   and cannot be answered by plain chat — by design.
4. **New blocker discovered, invalidating company-arm outputs so far**: the
   delivery card's completion report states the workspace is mounted
   read-only inside company role turns ("Write access is still
   unavailable; the runtime rejected the filesystem probe"), while the
   host workplace directory is writable and the task arm wrote real files
   there. Suspected cause: per-turn sandbox mode selection for company
   role execution (`execution_environment.sandbox`, bwrap present,
   `default_mode: workspace-write`). Until this is root-caused, company
   slots deliver blockage reports, not work — the Task-vs-Company
   comparison would be invalid.

Next engineering priority: root-cause the sandbox mode applied to company
role turns in the native runtime, then re-run one company slot cleanly.
